> 이 글은 사내 가상화 서버의 사전 조사 및 작업 계획을 정리한 글입니다. 마이그레이션·재구축 완료 실적으로 표현하지 않으며, 팀 작업 문서를 바탕으로 검토 흐름을 설명합니다.

### 한눈에 보는 사례

| 항목 | 내용 |
|---|---|
| 목적 | OS 및 VirtualBox 버전 업데이트를 위한 호스트 환경 정비 |
| 조사 대상 | 운영 가상화 호스트 2대와 임시·테스트 호스트 1대 |
| 주요 항목 | CPU, 메모리, 디스크, RAID, 네트워크, OS, VM 데이터 위치·사용량 |
| 계획 | 임시 환경 검증 → VM 순차 이관 → 운영 호스트 업데이트 → VM 복귀 |
| 현재 글의 범위 | 현황 조사, 자원 제약, 검증 및 복구 계획 |

## 1. 호스트 정비가 VM 서비스에 미치는 영향

가상화 호스트의 OS와 VirtualBox 환경을 정비하려면 호스트뿐 아니라 그 위에서 실행되는 VM의 서비스 영향도 함께 확인해야 합니다. 계획 문서는 이를 EOS 대응 작업으로 다루고 있습니다. 이 글은 특정 제품 버전의 공식 지원 종료일을 판정하는 글이 아니라 해당 내부 정비 계획을 정리한 기록입니다.

운영 서버를 바로 변경하는 대신, 임시 호스트를 먼저 준비하고 VM을 옮긴 후 기존 호스트를 정비하는 흐름이 제시됐습니다.

## 2. 호스트 자원·VM 현황과 이관 제약

| 구분 | 조사 항목 | 계획에 필요한 이유 |
|---|---|---|
| 호스트 자원 | CPU·메모리·디스크 용량 및 사용량 | 임시 호스트의 수용 가능 범위 판단 |
| 저장 구조 | RAID 구성, VM 데이터·스냅샷 위치 | 이관·백업 범위와 초기화 영향 파악 |
| 네트워크 | 사용 인터페이스, 브리지 및 VM 연결 설정 | 이관 후 접속 설정 확인 |
| 소프트웨어 | OS 및 VirtualBox 버전 | 신규 환경 검증 항목 정리 |
| VM 현황 | 용도, 자원 할당·사용량, 전원·사용 여부 | 이전 순서와 사용자 영향 파악 |

전원이 꺼진 VM이라고 해서 곧바로 미사용으로 분류할 수는 없습니다. 기록에는 사용 예정, 백업 보관, 확인 필요 상태도 있어 실제 사용 여부를 구분하는 과정이 필요했습니다.

일부 RAID 정보는 조사 당시 추정으로 남아 있었습니다. 추정값을 확정된 구성으로 옮기기보다, 실제 변경 전에 확인해야 할 항목으로 남기는 편이 맞습니다.

임시 호스트는 운영 호스트보다 자원이 작았습니다. 따라서 운영 VM 전체를 한 번에 옮길 수 있다는 가정으로 작업 순서를 확정할 수 없었습니다.

VM을 종료한 뒤 데이터를 옮기는 방식이므로 작업 중 서비스 중단이 발생합니다. 주요 서비스는 업무 영향이 적은 시간에 작업해야 하며, VM별 담당자와 정상 여부 확인 기준이 필요했습니다.

## 3. 임시 호스트를 이용한 순차 이관 방식

운영 호스트를 바로 재구축하지 않고 **임시 환경 검증 → VM 순차 이관 → 기존 호스트 업데이트 → VM 복귀** 방식을 선택했습니다. 변경 전에 새 환경에서 VM 부팅과 네트워크를 확인할 수 있고, 정상 동작을 확인할 때까지 기존 VM 데이터를 유지할 수 있기 때문입니다.

임시 호스트가 모든 VM을 수용하지 못할 가능성에 대비해 다른 운영 호스트로 분산 이전하는 시나리오도 포함했습니다. 한 번에 전체 환경을 변경하기보다 호스트별로 순차 적용해 영향 범위를 줄이는 계획입니다.

## 4. VM 이관 → 호스트 정비 → 복귀 작업 계획

1. **임시 환경 구성 및 검증**: 테스트 VM의 부팅, 네트워크, 저장 위치, 호스트 재부팅 후 동작을 확인합니다.
2. **첫 번째 운영 호스트의 VM 이관**: 서비스 영향을 고려해 VM을 종료하고 데이터를 이전·등록합니다.
3. **이관 상태 확인**: VM 부팅 → 네트워크 → 서비스 → 데이터 순으로 확인합니다.
4. **기존 호스트 업데이트**: 주요 설정·데이터 백업과 이관 VM의 정상 동작을 확인한 뒤 작업합니다.
5. **VM 복귀 및 재확인**: 원래 호스트로 복귀시킨 후 같은 확인 절차를 거칩니다.
6. **다음 운영 호스트에 순차 적용**: 앞선 작업의 검증 결과를 확인하고 다음 대상을 진행합니다.

VM을 종료한 후 이전하는 계획이므로 무중단 마이그레이션으로 표현하지 않았습니다. 주요 서비스는 업무 영향이 적은 시간에 작업하고, VM별 영향 범위와 순서를 사전에 정하는 접근입니다.

## 5. 이관 후 점검 항목과 원복 조건

임시 환경에서는 테스트 VM 생성·실행, 네트워크 통신, 데이터 저장 위치, 호스트 재부팅 후 정상 동작을 확인하도록 계획했습니다. 실제 VM 이관 후에는 **부팅 → 네트워크 → 서비스 → 데이터** 순서로 확인합니다.

이전 VM에서 이상이 발생하면 다음 단계로 넘어가지 않고 작업을 중단하는 것을 검증 게이트로 두었습니다. 이 글은 계획 단계이므로 테스트 결과나 성공 수치는 아직 없습니다.

### 원복이 가능한 시점 구분하기

이전 VM에서 부팅·네트워크·서비스 문제가 발생하면 다음 단계로 넘어가지 않고 작업을 중단해 원인을 확인하도록 계획돼 있습니다. 정상 동작 확인 전까지 기존 호스트의 VM 데이터를 유지하고, 필요하면 신규 호스트의 VM을 종료한 뒤 기존 호스트에서 다시 기동하는 흐름입니다.

다만 기존 호스트를 초기화한 뒤에는 같은 방식의 단순 복귀가 어려워집니다. 따라서 초기화 전에 별도 백업과 복구 가능 여부를 확인하는 조건이 함께 필요합니다. “기존 데이터를 남긴다”와 “호스트 초기화 이후에도 복구할 수 있다”는 구분해서 확인해야 할 내용입니다.

## 6. 작업 전에 확정해야 할 구성과 담당 범위

계획 문서에는 확장 기능의 실제 사용 여부와 적용 조건 검토가 남아 있고, 임시 호스트의 저장 구성·데이터 저장 위치도 구성표와 상세 절차 사이에 정리가 필요한 부분이 있습니다. 공개 글에는 이를 확정된 구축 결과처럼 옮기지 않았습니다.

실행 전에 확정할 항목은 다음과 같습니다.

- 임시 호스트의 최종 디스크·RAID·데이터 저장 구성
- 실제 이관 가능한 VM 조합과 자원 여유
- 추가 확장 기능의 필요 여부와 적용 조건
- VM별 서비스 확인 담당자, 작업 시간 및 중단·원복 기준

가상화 환경의 버전 정비는 설치 절차만으로 끝나지 않습니다. 운영 대상의 현황, 임시 수용 자원, 서비스 확인 순서, 원복 가능 시점을 함께 정리해야 실행 가능한 계획이 됩니다.

이 사례가 보여주는 범위는 조사와 변경 계획입니다. 실제 작업 완료 기록이 추가되면 계획과 실행의 차이, 이관 중 발생한 문제, 최종 검증 결과를 후속 글로 연결할 수 있습니다.

> 내부 폴더명, 조직명, 장비 식별자와 네트워크 정보는 익명화했습니다. 수치는 작업 기록에 적힌 표시값을 기준으로 작성했습니다.

### 한눈에 보는 사례

| 항목 | 내용 |
|---|---|
| 문제 | 백업 NAS 저장공간 부족 및 운영 NAS와의 데이터 차이 |
| 분석 | 공유폴더별 파일 수 확인, CSV 목록 추출, 경로·크기·수정일 비교 |
| 보존 판단 | 백업 NAS에만 존재하는 9개 폴더 약 9.65TB 확인, 그중 8개 폴더 보존 대상으로 선정 |
| 처리 | 별도 NAS로 데이터 이관·검증 후 정리 대상 삭제 |
| 결과 | 사용량 23.8TB → 15TB, 여유 공간 569.8GB → 9.3TB |

## 1. 문제 정의

임직원 운영 NAS를 백업하는 NAS에서 저장공간 부족 문제가 발생했습니다. 백업 NAS는 약 510만 개, 운영 NAS는 약 439만 개의 파일을 가지고 있었습니다. 단순 파일 수로는 약 71만 개 차이였지만, 이 숫자가 곧 삭제 가능한 파일 수는 아니었습니다.

백업 NAS에만 남아 있는 과거 업무자료가 있는 한편, 공통 공유폴더 중에는 오히려 백업 NAS의 파일 수가 적은 곳도 있었습니다. 따라서 전체 용량과 파일 수만으로 백업 완전성이나 데이터 보존 필요 여부를 판단하지 않고, 폴더 및 파일 단위 비교로 범위를 좁혔습니다.

## 2. 환경과 제약

분석 대상은 수백만 개 파일과 수십 TB 규모의 운영·백업 NAS였습니다. 서비스 중인 데이터를 다루기 때문에 용량 차이만 보고 삭제할 수 없었고, 백업 NAS에만 남은 과거 자료의 보존 여부도 먼저 판단해야 했습니다.

제공된 작업 기록에는 파일 내용의 해시 대조 결과가 없었습니다. 따라서 비교 가능한 근거는 공유폴더명, 상대경로, 파일명, 크기, 수정일이었으며, 이 기준의 일치를 파일 내용 자체의 동일성으로 확대해 표현하지 않았습니다.

## 3. 설계 선택

바로 정리하는 대신 **현황 파악 → 동일 형식의 목록 생성 → 차이 분류 → 보존 대상 선정 → 별도 장비 이관·검증 → 원본 정리** 순서를 선택했습니다.

파일이 많은 환경에서 반복 비교할 수 있도록 GUI의 표시 용량만 보는 방식보다 CSV 목록을 사용했습니다. 또한 RAID 구성은 디스크 장애 대응 수단으로, 별도 장비 이관은 데이터 보존 수단으로 구분했습니다.

## 4. 구현

### 비교 가능한 목록 만들기

두 NAS의 공유폴더 파일 목록을 같은 형식의 CSV로 추출했습니다. 파일 수가 많아 NAS별·공유폴더별로 목록을 나누었습니다.

| 필드 | 확인 목적 |
|---|---|
| 공유폴더명 | 어떤 공유 영역의 파일인지 구분 |
| 상대경로·파일명 | 서로 다른 NAS에서 대응되는 파일 찾기 |
| 파일 크기(Byte) | 크기 차이와 사용량 파악 |
| 수정일 Unix Time·수정일시 | 수정 시점 차이 비교 및 사람이 확인할 기록 확보 |

저장공간 사용 원인을 파악하는 단계에서는 NAS 시스템 파일도 목록에 포함했습니다. 다만 목록에 포함했다는 이유로 일반 업무 파일과 같은 삭제 기준을 적용한 것은 아닙니다.

### 비교 결과를 보존 판단으로 연결하기

비교 항목은 같은 경로의 파일 중 크기·수정일이 일치하는 경우, 한쪽에만 존재하는 경우, 크기 또는 수정일이 다른 경우, 공유폴더 자체가 다른 경우로 나누었습니다.

여기서 경로·크기·수정일이 같다는 것은 **메타데이터 기준의 일치**입니다. 파일 내용의 해시를 대조한 기록은 없으므로 내용까지 동일하다고 검증한 것으로 표현하지 않았습니다.

백업 NAS에만 존재하는 9개 폴더의 합계 사용량은 약 9.65TB로 확인됐습니다. 이 중 보존 불필요로 분류한 1개 폴더를 제외하고 8개 폴더를 보존 대상으로 선정했습니다. 따라서 “9.65TB를 모두 삭제했다”거나 “9.65TB의 공간을 그대로 확보했다”는 설명은 실제 작업과 다릅니다.

### 보존용 NAS 확보와 데이터 이관

유휴 NAS의 디스크 구성을 확인해 4TB 디스크 4개가 장착된 장비를 보존 장비로 선정했습니다. 작업 계획에는 디스크 장애에 대비한 RAID5 구성이 제시돼 있고, 별도 장비 세팅 이후 이관 작업으로 이어졌습니다.

기록된 이관 흐름은 다음과 같습니다.

1. 보존 장비를 설치하고 데이터 이관 경로를 준비했습니다.
2. 공유폴더 동기화를 등록하고 용량이 작은 폴더부터 복제를 진행했습니다.
3. 동기화에서 복제되지 않은 일부 휴지통 내 파일은 SSH를 통해 별도로 복제했습니다.
4. 보존 대상 8개 폴더의 데이터 이전 완료 여부를 확인했습니다.
5. 보존 데이터 이관 및 검증 후 원래 백업 NAS의 정리 대상 데이터를 삭제했습니다.

RAID 구성과 별도 장비로의 복제는 각각 다루는 위험이 다릅니다.

## 5. 검증

작업 기록상 보존 대상 8개 폴더의 이전 완료 여부를 확인한 뒤 정리 대상 데이터를 삭제했습니다. 실제 검증 명령이나 해시 대조 결과는 제공된 기록에 없어 덧붙이지 않았습니다.

작업 전후 저장공간은 다음과 같이 확인했습니다.

| 지표 | 작업 전 | 작업 후 |
|---|---:|---:|
| 사용량 | 23.8TB | 15TB |
| 여유 공간 | 569.8GB | 9.3TB |

보존이 필요한 데이터를 별도 장비로 옮긴 뒤 정리하여 백업 NAS의 여유 공간을 확보했습니다. 약 9.65TB는 분석 과정에서 확인한 폴더 사용량이며, 작업 전후 여유 공간 차이와 동일한 지표가 아닙니다. 표시 단위와 반올림이 포함된 값이므로 불필요하게 정밀한 개선율도 계산하지 않았습니다.

## 6. 개선점

스토리지 정리는 삭제 작업 이전에 데이터의 성격을 구분하는 작업이었습니다. 운영 NAS에 없다는 사실만으로 불필요한 데이터라고 판단할 수 없고, 백업 NAS가 더 크다고 백업이 완전하다고 판단할 수도 없었습니다.

다시 수행한다면 비교 기준 시각을 고정하고, 파일 해시 또는 표본 검증 기준, 복제 예외 목록, 이관 전후 파일 수·용량을 자동 기록하도록 개선할 수 있습니다. 보존 기간과 삭제 승인 기준도 문서화하면 데이터 정리의 판단 근거를 더 명확하게 남길 수 있습니다.

*근거: 2026년 8월 백업 NAS 데이터 보존 및 저장공간 확보 작업 기록. 원본 목록과 내부 화면은 공개하지 않습니다.*

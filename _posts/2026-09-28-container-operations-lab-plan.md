> 이 글은 앞으로 수행할 실습의 범위와 검증 기준입니다. 서버 생성, 배포 및 장애 테스트를 완료했다는 의미가 아닙니다.

## 1. 실습의 목적

실무에서는 전원, 네트워크, 서비스가 각각 정상인지 구분하는 점검 과정이 중요했습니다. 이 확인 흐름을 클라우드 VM과 컨테이너 환경에 적용해 보는 것이 이번 실습의 목적입니다.

1주 안에 다룰 범위는 EC2의 Linux 환경, Docker 기반 배포, k3s에서의 애플리케이션 실행과 복구 확인입니다. 구성 범위를 작게 유지하고 실행 기록을 남기는 데 집중하려고 합니다.

## 2. 단계별 구성

```text
1단계: 사용자 → EC2 Linux → Docker Compose → API / 데이터 저장소
2단계: 사용자 → EC2 Linux → k3s → Service → API Pod
```

Compose와 k3s는 단계별로 검증하고, 전환 시 기존 서비스의 실행 상태와 포트 사용을 확인할 계획입니다. 첫 Kubernetes 검증은 상태를 저장하지 않는 간단한 API를 대상으로 잡아, DB 데이터 관리와 Pod 복구 실험을 분리합니다.

단일 EC2에서 여러 Pod를 띄우는 구성으로는 호스트 자체의 장애까지 견디는 고가용성을 입증할 수 없습니다. 실습 결과는 Pod 수준의 복구와 상태 점검 범위로 설명할 예정입니다.

## 3. 7일 작업 계획

| 일정 | 할 일 | 남길 증거 |
|---|---|---|
| 1일차 | EC2 환경 및 접근 범위 설정, SSH 접속 확인 | 익명화한 구성도·접속 기록 |
| 2일차 | 간단한 API와 상태 확인 경로 준비 | 정상·실패 응답 예시 |
| 3일차 | Docker 이미지 빌드 및 실행 | Dockerfile·실행 로그 |
| 4일차 | Compose 배포, 네트워크·데이터 저장 확인 | 구성 파일·재시작 전후 기록 |
| 5일차 | k3s에 Deployment·Service 배포 | 배포 YAML·Pod 상태 |
| 6일차 | Replica·상태 검사·Pod 삭제 후 복구 확인 | 이벤트·상태 변화·요청 결과 |
| 7일차 | 결과 정리, 남은 자원과 비용 확인 및 정리 | 검증 표·회고·자원 정리 기록 |

## 4. 성공 여부를 무엇으로 판단할까

| 검증 항목 | 확인할 내용 |
|---|---|
| 서비스 접근 | 외부 요청이 의도한 경로로 API까지 도달하는가 |
| 컨테이너 상태 | 실행 상태와 실제 응답이 일치하는가 |
| 데이터 저장 | Compose 서비스 재생성 이후에도 보존 대상 데이터가 남는가 |
| Pod 복구 | Pod 삭제 후 새 Pod가 만들어지고 준비 상태에 도달하는가 |
| 상태 검사 | 준비되지 않은 Pod가 트래픽 대상에서 제외되는가 |
| 요청 영향 | 복구 중 연속 요청에서 실패가 발생하는지 기록했는가 |
| 자원 정리 | 실습 종료 후 불필요한 클라우드 자원을 정리했는가 |

Pod가 다시 생성됐다는 사실과 사용자 요청이 한 번도 실패하지 않았다는 사실은 별개의 결과로 기록할 예정입니다. 실행 시점의 설치 방법과 서비스 조건은 공식 문서로 확인하고, 사용한 버전도 결과 글에 함께 남깁니다.

## 5. 결과 글에 추가할 자료

- 실제 사용한 구성 파일과 저장소 링크
- 사용한 버전과 실습 환경
- 장애를 재현한 방법과 전후 상태
- 성공한 항목, 실패한 항목, 해결하지 못한 제약
- 실무의 서버·스토리지 점검 경험과 연결된 배운 점

아직 실행 증거가 없으므로 이 글의 상태는 **실습 계획**으로 유지합니다.
